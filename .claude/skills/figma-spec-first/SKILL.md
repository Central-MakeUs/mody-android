# 시안대로 한 번에 짜기

UI 가 시안과 어긋나는 건 실력이 아니라 **순서** 문제다. 값을 손에 넣기 전에 코드를
쓰기 시작하면 기억으로 채우게 되고, 기억은 틀린다.

**규칙 하나: 스펙 시트를 출력하기 전에는 간격 값을 쓰지 않는다.**

## 왜

한 프로젝트에서 디자인 토큰 검사 CI 를 붙인 **다음 날** 화면 두 개에서 14건이 틀렸다.
CI 는 초록불이었다 — 간격은 토큰이 아니라 검사 범위 밖이었다. 원인 분류(누적 18건):

| 원인 | 비율 | 예 |
| --- | --- | --- |
| 기본값 관성 (손이 먼저 `24` 를 침) | 9/18 | `24→36`, `24→28`, `24→32` |
| 좌표 뺄셈을 안 함 | 6/18 | `32→37` (윗 블록 끝 780, 아랫 행 817) |
| 행 높이 기준 착각 | 1/18 | 이미지 91 vs 텍스트 78.4 |
| 화면 내 패딩이 하나라고 가정 | 1/18 | 상단 36, 하단 섹션 24 |
| 같은 컴포넌트를 두 번 그림 | 1/18 | 두 화면 중 하나만 시안대로 |

전부 **구현 시점에 정확한 숫자가 없어서** 났다. 리뷰로는 안 걸린다 — 2~12 차이를
눈으로 잡는 사람은 없다.

규칙을 몰라서가 아니라 값을 얻는 순서가 뒤였다. 그래서 이건 자동화가 아니라 순서를
뒤집는 절차다: `구현 → 대조 → 정정`(3번 일함) 을 `스펙 시트 → 구현`(1번) 으로.

---

## STEP 0 — 도구 등급

Figma MCP 는 도구마다 리턴하는 게 다르다. **틀리면 값이 추정이 된다.**

| 도구 | 리턴 | 판정 |
| --- | --- | --- |
| `get_screenshot` | 이미지(PNG) | ❌ **값 근거로 쓰지 마라** |
| `get_metadata` | 정확한 x/y/w/h | ✅ 좌표·간격 |
| `get_variable_defs` | 바인딩된 변수 원본값 | ✅ 색·타이포 |
| `get_design_context` | 스타일·컴포넌트 컨텍스트 | ✅ 어떤 토큰이 쓰였는지 |

스크린샷에서 값을 읽으면 안티에일리어싱된 픽셀에서 hex 를 뽑거나 높이를 눈대중하게 된다.
나머지 셋은 Figma 가 들고 있는 **원본값을 그대로** 준다. 추정이 개입할 자리가 없다.

스크린샷은 "무엇이 어디 있나" 파악에만 쓴다. **숫자는 절대 안 읽는다.**

## STEP 1 — 스펙 시트 (코드 쓰기 전)

화면 노드 하나당 한 번:

```
get_metadata(nodeId)        # 절대좌표 전부
get_design_context(nodeId)  # 토큰·컴포넌트명
```

> 캔버스 루트에 `get_metadata` 를 통째로 부르지 마라. 응답이 감당이 안 된다.
> 화면/섹션 단위 노드로 좁힌다.

받은 절대좌표를 **그 자리에서 간격으로 변환해 적는다.** 뺄셈은 여기서 한 번만 한다.

```
탭 바 끝      162
칩 시작       198   → gap 36
첫 줄 끝      531
둘째 줄       533   → gap 2
시상대 끝     780
4등 행        817   → gap 37
```

**이 표를 대화에 실제로 출력하고 나서 코드를 쓴다.** 머릿속에만 있으면 안 한 것이다 —
출력된 표가 이 절차를 밟았다는 유일한 증거고, 나중에 값을 되짚을 때도 이게 근거다.

`36`·`2`·`37` 이 손에 있으면 `24` 를 칠 일이 없다.

## STEP 2 — 변환 규칙

**1. 모든 간격은 뺄셈 결과다.** 기억·감·"보통 이 정도"로 쓴 값은 전부 틀렸다고 간주한다.
스펙 시트에 없는 숫자를 쓰려는 순간 멈추고 STEP 1 로 돌아간다.

**2. 행 간격은 그 행에서 제일 큰 요소의 바깥 테두리 기준.** 중앙 정렬이면 작은 요소는
안쪽으로 들어와 있다. 텍스트 윗변으로 재서 42 가 나왔는데 실제는 36 인 식으로 틀린다.
행의 위아래를 정하는 게 무엇인지(높이 최대 요소) 먼저 확인한다.

**3. 가로 패딩은 블록마다 다시 잰다.** 한 화면 안에 24 와 36 이 공존한다.
"이 화면 패딩은 X" 라는 가정을 하지 않는다.

**4. 컴포넌트명이 보이면 코드에도 공용 컴포넌트가 있어야 한다.** `get_design_context` 가
`chip` 같은 이름을 주면 코드에서 그 컴포넌트를 찾는다. 없으면 만든다. 화면마다 따로
그리면 반드시 갈라진다 — 한 곳만 시안대로 남는다.

**5. 색·타이포는 숫자가 아니라 토큰 이름으로 옮긴다.** `#6A6A6A` 가 아니라 `Gray07`.
`get_variable_defs` 가 준 변수명을 프로젝트의 코드 토큰에 매핑한다. 숫자를 직접 쓰면
시안이 바뀔 때 추적이 끊긴다. 매핑표가 프로젝트에 있으면 그걸 따르고, 없으면 만든다
(Figma 변수명과 코드 토큰명은 대개 다르다).

## STEP 3 — 근거를 코드에 남긴다

실측값은 자주 어중간하다(`37`, `28`, `2`). 근거가 없으면 다음 사람이 "오타네" 하고
반올림해 되돌린다. **값 옆에 출처를 적는다 — 노드 ID 와 뺄셈 근거를 같이.**

```kotlin
// 시안 실측 36 (서브탭 바 끝 162 → 칩 198, 251:2309).
Spacer(modifier = Modifier.height(36.dp))
```

```swift
// 시안 실측: 배경 423~836, 내용 455~804 → 위 32 / 아래 32.
.padding(.vertical, 32)
```

커밋 메시지에도 같은 형식으로 남긴다 — 나중에 왜 그 값인지 되짚을 유일한 기록이다.

## 체크리스트

구현 전:
- [ ] `get_metadata` 로 좌표 뽑았나
- [ ] 좌표 → 간격 뺄셈표를 **대화에 출력**했나
- [ ] `get_design_context` 로 토큰·컴포넌트명 확인했나

구현 중:
- [ ] 쓰는 간격 값이 전부 뺄셈 결과인가 (기억으로 쓴 값 0건)
- [ ] 행 간격을 최대 요소 기준으로 쟀나
- [ ] 가로 패딩을 블록마다 다시 쟀나
- [ ] Figma 컴포넌트명에 대응하는 공용 컴포넌트를 썼나
- [ ] 색·타이포를 토큰 이름으로 썼나

구현 후:
- [ ] 어중간한 값 옆에 노드 ID + 뺄셈 근거 주석이 있나
