# 토큰 lock + CI 대조

[SKILL.md](SKILL.md) 의 부록. 절차가 아니라 **인프라 결정**이라 따로 뺐다.
스킬 본문(STEP 0~3)만으로도 화면은 짤 수 있다 — 이건 그 위에 얹는 선택지다.

## 간격은 왜 자동 검사가 안 되나

색·타이포는 토큰이라 스냅샷에 박아 CI 로 대조할 수 있다. **간격은 대체로 못 한다.**

실제 시안 간격 예: `36, 37, 28, 27.7, 22.5, 2, 13, 30, 35.5`

4/8 배수도 아니고 정수도 아니다. 스페이싱 스케일 토큰을 만들 수 없고, 토큰이 없으면
대조할 정답지도 없다.

시안이 엄격한 스페이싱 스케일(4/8 배수 등)을 따르는 프로젝트라면 얘기가 달라진다 —
그때는 간격도 토큰화해 검사 범위에 넣는다. **먼저 시안 간격 값을 훑어 스케일이 있는지
확인하고 판단한다.** 없으면 실측 + 근거 주석(SKILL.md STEP 3)이 유일한 답이다.

## 색·타이포는 굳힐 수 있다

한 프로젝트에서 타이포 토큰의 `lineHeight` 가 아랫줄에서 복사돼 25곳이 2.8sp 씩
어긋난 채 리뷰를 통과했다. "살짝 빽빽한데요"로는 안 걸리는 종류다.

- `get_variable_defs` 로 뽑은 값을 lock JSON 으로 커밋
- CI 는 그 JSON 과 코드 토큰 선언부만 대조. **Figma 를 호출하지 않는다** → 인증키 불필요,
  네트워크 실패로 빌드가 깨지지 않음, 같은 커밋이면 언제 돌려도 같은 결과
- 커버리지가 부분적이면 `_unverified` 에 명시해 "전부 검증됨"으로 읽히지 않게 한다
- 시안 전체가 따르는 불변식(예: `lineHeight = fontSize × 1.4`)이 있으면 lock 에 없는
  토큰까지 전부 적용한다 — 부분 커버리지를 전수 규칙으로 보완. 위 25곳 사례를 잡은 게
  스냅샷이 아니라 이 규칙이었다

## 대가

**시안이 바뀌면 정답지가 낡는다.** 낡은 정답지는 맞는 코드를 막는 역효과를 낸다 —
검사가 없는 것보다 나쁘다.

시안 변경이 잦으면 `GET /v1/files/{key}?depth=1` 의 `lastModified` 를 폴링해 갱신 PR 을
자동 생성하되, **그 워크플로만 인증키를 갖고 검사 CI 는 토큰 없이** 둔다.

## 이 스킬이 검사하지 않는 것

lock 대조는 **토큰 선언부**만 본다. 선언이 맞아도 화면에서 엉뚱한 토큰을 쓰면 안 걸린다.
`gray07` 자리에 `gray08` 을 써도 통과한다 — 둘 다 선언은 정확하니까.

그건 STEP 2 규칙 5(토큰 이름으로 옮기기)와 리뷰의 몫이다. CI 초록불을 "시안대로다"로
읽으면 안 된다. 실제로 그렇게 읽었다가 다음 날 14건이 났다.
